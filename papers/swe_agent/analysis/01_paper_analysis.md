# 01. 논문 분석: SWE-agent (arXiv:2405.15793v3)

SWE-agent: Agent-Computer Interfaces Enable Automated Software Engineering. Yang, Jimenez, Wettig, Lieret, Yao, Narasimhan, Press (Princeton). NeurIPS 2024 포스터. 분석 판본은 arXiv v3(2024-11-11, 본문 10쪽과 부록 108쪽).

## 1. 문제와 주장

언어 모델 에이전트는 사람용 도구(리눅스 셸, Python 인터프리터)를 그대로 쓰는 것이 보통이다. 저자들은 사람에게 IDE가 필요하듯 LM 에이전트도 **자기에게 맞춘 인터페이스**가 필요하다고 보고, 에이전트와 컴퓨터 사이의 추상 계층을 **에이전트-컴퓨터 인터페이스(ACI)**라 부른다(§1, §2). ACI는 사용할 명령의 집합과 환경 피드백의 형식, 그리고 기록(history)을 어떻게 다시 프롬프트로 묶는지까지 포함한다(§2).

핵심 주장은 둘이다(§1).

1. 모델 가중치를 바꾸지 않고 ACI 설계만으로 SWE-bench 성능이 크게 오른다.
2. 그 결과물인 SWE-agent는 GPT-4 Turbo로 SWE-bench 전체 2,294문항 중 12.47%(286개), Lite 300문항 중 18.00%(54개)를 푼다. 이전 최고였던 비대화형 RAG는 3.8%였다.

## 2. 방법

### 2.1 설계 원칙 네 가지 (§2)

| # | 원칙 | 논문이 드는 근거 |
|---|---|---|
| 1 | 행동은 단순하고 이해하기 쉬워야 한다(옵션이 적고 설명이 짧게) | §3 명령 목록, 표 4 |
| 2 | 행동은 간결하고 효율적이어야 한다(중요한 동작은 한 번에) | 편집·검색 비교(그림 5, 6, 표 3) |
| 3 | 환경 피드백은 정보가 있되 간결해야 한다 | 편집 뒤 파일 뷰어 자동 갱신, 표 3 |
| 4 | 가드레일이 오류 전파를 막고 회복을 앞당긴다 | linting 어블레이션(표 3) |

원칙은 (1) 개발 분할에서 에이전트 행동을 손으로 관찰해 문제를 찾고, (2) 격자 탐색으로 설정을 고르는 두 방식으로 얻었다(§2, §4). 즉 원칙은 가설 정리이고 사전 등록된 검정이 아니다.

### 2.2 구성 요소 (§3, 표 4, 부록 A.1)

- **검색·탐색:** `find_file`, `search_file`, `search_dir`. 결과는 요약해서 보여 주고 "너무 많으면"(논문은 50개) 결과를 내지 않고 쿼리를 좁히라고 안내한다.
- **파일 뷰어:** `open`, `goto`, `scroll_up/down`. 한 번에 최대 100줄, 파일 경로·전체 줄 수·위아래 생략 줄 수·줄 번호를 붙인다.
- **편집기:** `edit <n>:<m>` + 대체 텍스트 + `end_of_edit`. 줄 범위를 한 번에 바꾸고, 편집 뒤 뷰어가 자동으로 갱신된다. **linter가 편집에 들어 있어** 문법 오류가 생기면 편집을 버리고 "편집 전후"를 보여 준다. `create`와 `submit`도 있다.
- **컨텍스트 관리:** 형식 오류 메시지는 첫 번째 것만 남기고, 출력이 없으면 "Your command ran successfully and did not produce any output"를 넣고, 최근 5개 관찰 이전은 한 줄로 접는다.
- 매 단계 ReAct 방식(thought + command)이다. 셸 위에 얹혀 있어 일반 리눅스 명령도 쓸 수 있다.

### 2.3 설정 (§4, 부록 A.3, B.1)

모델은 GPT-4 Turbo(gpt-4-1106-preview)와 Claude 3 Opus(claude-3-opus-20240229). 인스턴스당 비용 상한 $4(초과하면 지금까지의 편집을 자동 제출). 창 크기·기록 처리·temperature를 개발 분할 37개 인스턴스(모델·설정당 5회 표본)에서 훑어 temperature 0.0, 창 100줄, 최근 5개 관찰을 골랐다(표 5). 기준선은 BM25 RAG(SWE-bench 원 논문)와 Shell-only(InterCode식 셸 상호작용).

## 4. 한계

논문이 인정한 것(부록 E.3): 도구가 적다(정적 분석·웹 탐색 없음), ACI 개발이 수작업이다, 프로그래밍 과제만 다뤘다.

우리가 보태는 것(근거는 03, 04):

- 어블레이션 각 칸은 **단일 실행**이고, 변형별 분산이 없다. 3%p 차이는 표 10의 실행 간 변동으로는 구분이 어렵다(`03` §3).
- Shell-only 대비 "+10.7%p"는 서로 맞지 않는 조건(SWE-agent는 데모 있음, Shell-only는 데모 없음)을 비교한 값이다(`03` §2).
- Claude 3 Opus 수치는 논문 안에서 서로 다르고(Lite 13.00 대 11.67), 공개 결과 파일과도 다르다(`03` §6).
- 평가는 SWE-bench의 숨은 테스트 통과 여부 하나다. 통과가 곧 올바른 수정이 아님을 이후 연구가 보였다(`02` §3).
- 개발 분할로 설계했으므로 ACI 원칙은 SWE-bench 한 과제군에서 얻은 것이다. 다른 모델에 대한 이식성은 Claude 3 Opus 한 개로만 확인했다(표 1, 성능은 더 낮음).
- 이 논문의 모델(2024년 초)과 이후 모델에서 ACI의 영향이 같다는 근거는 없다. 저자들 스스로 후속 mini-swe-agent에서 "도구 대부분이 필요 없다"고 말한다(`02` §3, `04` §5).
