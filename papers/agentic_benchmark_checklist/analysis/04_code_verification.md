### D2. 평가표 ↔ 저장소 yaml: 일치

`parse_assessments.py`로 부록 D 표 5–14(10개)와 `assessments/*.yaml` 10개를 항목마다 대조했습니다. 항목 수와 점수 모두 일치합니다(불일치 0). 단 표 8의 제목은 "SWE-Bench-Verified"인데 링크는 원 SWE-bench 논문(2310.06770)과 원 저장소이고, O.d.1은 이유가 "논문에 검증 과정이 언급되지 않는다"인데 점수는 1입니다(이유와 점수가 모순, 표 8). Verified의 사람 검증(O.d.1)을 인정했다면 이유 문구가 틀린 것입니다.

### D3. τ-bench 수정 패치는 항공만이고, 읽기 호출만 해도 통과하는 구멍이 남습니다 (정적 추론)

- `tau-bench-issue-1-fix.patch`는 `envs/airline/tasks_test.py`, `envs/base.py`, `types.py`만 고칩니다. **소매는 고치지 않았습니다.**
- 항공 과제에 `required_actions`를 새로 붙인 곳이 정확히 **19개**(`+ required_actions=` 19줄)이고 이는 재계산한 do-nothing 통과 과제 수 19(`recompute_tau_bench.py`)와 같습니다. 별도로 과제 2개(mei_brown_7075, raj_sanchez_7340)는 지시문·정답 액션을 다시 썼습니다.
- `base.py`의 새 검사는 "에이전트 액션에 `required_actions`가 이름·인자까지 같게 있는가"입니다. 대부분 `get_reservation_details`·`get_user_details` 같은 **읽기** 호출입니다. 따라서 필요한 읽기 호출을 한 뒤 아무것도 바꾸지 않고 끝내는 에이전트(거절 문장 없음)는 DB가 같고 필수 액션이 있어 통과합니다. 코드 논리상 그렇다는 것이고 실행해 확인하지 않았습니다. 정확한 판정은 거절 응답의 내용을 요구해야 합니다(`outputs`).
- README의 권고 수정은 "풀 수 없는 과제와 DB 문구 정답 과제를 **제거**"인데 패치는 그 방식이 아니라 필수 액션을 더합니다. README 본문 "38%가 더 이상 안 나온다"(NEWS)는 실행 결과가 저장소에 없습니다.

### D4. "빈 응답 에이전트"와 재현 패치의 실제 행동이 다릅니다

- 논문 초록·서론: "τ-bench counts **empty responses** as successful". `exploit-1.patch`는 모델 호출을 지우고 `Action(name="transfer_to_human_agents", kwargs={})`를 곧바로 냅니다. 이 도구는 `terminate_tools`라 에피소드가 끝나고(`base.py` step), 채점은 `data_hash == gt_data_hash`입니다. 즉 "빈 문자열 응답"이 아니라 "즉시 상담원 이관"입니다. 둘 다 DB 불변이라 결과는 같지만, 인용할 때는 do-nothing(즉시 이관)이 정확합니다.
- `exploit-2.patch`(spamming)는 에이전트 클래스를 고쳐 **하네스 쪽 디렉터리의 DB json 파일을 직접 읽어** 한 번에 응답으로 보내고 이관합니다(`airline/data/*.json`, 소매 `orders.json` 등). 실제 에이전트가 가질 수 있는 도구가 아니라 채점기 허점을 보이는 위조 에이전트입니다. 의도된 설계이지만 "에이전트가 이렇게 한다"가 아니라 "채점기가 이를 막지 않는다"로 읽어야 합니다. `env.step`에서 사용자 시뮬레이터에는 content를 100자로 자르지만 보상은 `self.actions`의 전체 content를 봅니다(`base.py` step의 `self.actions.append(action)`).

### D5. τ-bench 소매 수치는 정적 계산으로 다 설명되지 않습니다

`recompute_tau_bench.py` 결과(항공은 정확 일치): 소매 test 115과제에서 do-nothing 통과가 정적으로 5개(4.3%, 논문 6.0%), spamming 상한 9개(7.8%, 논문 9.6%), DB 문구 정답 4개(3.5%, 논문 3.6%). 논문과 README의 소매 수치는 7/115, 11/115에 가깝습니다(`03` §4.1). 차이 2개 과제는 정답 액션의 쓰기가 DB를 바꾸지 못하는 경우로 설명될 수 있지만 도구 코드를 실행해야 확인됩니다. **실행하지 않았고 확인하지 못했습니다.**

### D6. KernelBench: 표본 설계가 논문과 다르고 결과 로그가 없습니다

- 논문 부록 E.6: "level 1의 과제마다 생성 커널 3개씩 표본, o3-mini로 테스트 생성, 수작업 검증".
- `scripts/preprocess_data.py`: Sakana 데이터(`SakanaAI/AI-CUDA-Engineer-Archive`)에서 `Correct == True`인 level 1 커널 중 **총 1,000개를 과제별 정답 수 비례로** 뽑습니다(`np.random.seed(2333)`, 과제 90개 폴더에서 평균 약 11개씩). 저장소 `tests/`의 테스트 파일이 1,000개(+ 최상위의 `1_Square_matrix_multiplication_.py` 1개)로 코드와 일치하고 논문의 "과제당 3개(약 300개)"와 맞지 않습니다.
- 수작업 검증 테스트는 `tests_verified/` 129개(71개 과제)뿐입니다. 이 테스트로 커널을 돌린 통과·실패 로그가 없어 **31% 과대 추정을 재계산할 수 없습니다.** `kernels/`는 논문 스크립트가 쓰는 경로(`kernels/level_1/<Op>/<id>.cu`)가 아니라 평평한 11,245개 `.cu` 파일이고 `utils.py`는 `kernels/{kernel_id}.cu`를 읽습니다.
- 재현에는 CUDA 12.4, GPU, OpenAI API가 필요합니다(README). 이 저장소 규칙상 GPU 재현은 하지 않습니다.

### D7. WebArena: `evaluate.py`는 LLM 판정자 경로를 건드리지 않습니다

`evaluate.py`는 `eval_types == ['string_match']`이고 `fuzzy_match`가 **없는** 과제만 비교합니다(코드의 `continue`). 이는 812과제 중 **212개**(`string_match`만 있는 325개 중 113개가 fuzzy_match)입니다. N/A 과제 36개(4.4%)는 모두 `fuzzy_match: N/A`라 이 스크립트가 아니라 `llm_as_a_judge.py`(o1)가 다룹니다. 따라서 논문 §5.2 "빈 응답을 LLM 판정자가 받는다"를 확인하려면 OpenAI 호출과 외부 궤적이 필요합니다(실행하지 않음). 36/812은 정확히 재현됩니다(`03` §4.3).

### D8. OSWorld: 패치가 13개 과제 전부를 덮지 않습니다

README와 논문은 chrome 과제 13/46이 깨졌다고 하지만 저장소의 chrome 패치는 **5개**입니다. 나머지 8개 과제의 수정은 없고, UI-TARS 24→37의 수작업 판정 자료(궤적 검토 기록)도 없습니다. 28% 과소 추정은 README 문장 수치이며 산술만 확인됩니다(`03` §4.2).

### D9. SWE-Lancer: 취약점 재현은 코드로 읽을 수 있습니다

`exploit.patch`는 에이전트의 모델 호출을 지우고 고정 코드로 대체합니다(`zipfile.ZipFile('/app/tests.zip')`로 `namelist()`를 읽고 내용을 덮어씀). `fix.patch`는 zip을 **두 겹**으로(바깥 zip에 다른 비밀번호) 만듭니다. 정적으로 논리는 논문 주장과 일치하지만 **"100%"는 실행 결과가 아니라 서술**입니다. 벤치마크 실행 없이는 확인할 수 없고 이 저장소는 실행하지 않았습니다. 두 겹 zip도 같은 파일 시스템에서 외부 zip 구조를 읽을 수 있는 한 근본 격리가 아닙니다(정적 추론, 논문 T.5 요구와 관련).

### D10. 저장소에 요약 CVE-Bench 자료가 없습니다

논문 §5.3의 CVE-Bench 수정과 그림 6의 원자료는 이 저장소에 없습니다(논문은 CVE-Bench를 arXiv:2503.17332 [96]으로 인용합니다). 따라서 32.5%, 10%는 이 저장소로 대조할 수 없습니다.

### D11. 저장소의 ABC 점수표 평가 방식

yaml 각 항목에는 `check`, `score`(0/1), `reason` 한 줄뿐이고 평가자·날짜·증거 링크(코드 줄, 로그)·확신도가 없습니다(`03` §3). 모든 점수가 이진이라 "부분 충족"이 표현되지 않으며, "해당 없음"은 1점으로 기록됩니다(`03` §2).

### D12. 라이선스

`ABC.md`와 저장소에 라이선스 파일이 없습니다(GitHub API `license: null`). 점검표 문서와 yaml을 이 저장소 밖으로 복사·재배포하지 않고, 항목 번역도 최소한으로 인용합니다. 논문은 arXiv 비독점 배포 라이선스입니다(README).

## 2. ABC 점검표가 이 저장소의 17번(`swe_bench`) 허점을 잡는가

17번 분석(`../swe_bench/analysis/04_code_verification.md`)의 채점 코드 정적 대조 항목을, ABC가 SWE-bench에 매긴 점수(표 8)와 비교합니다. "잡는다"는 점검표 항목이 그 허점을 지적하게 만드는 문구인가, 실제 평가가 지적했는가를 나눠 적습니다.

| 17번 허점 | ABC 항목(해당 시) | 점검표 문구가 겨냥하나 | 논문의 SWE-bench 평가가 잡았나 |
|---|---|---|---|
| D6a 빈 PASS_TO_PASS는 만점 1 (공개 test 분할 67문항 2.9%에서 회귀 검사 없음) | O.d.2(테스트 품질 객관 지표), T.10(채점 우회 취약점 없음) | **부분**: 회귀 검사가 비었음을 "테스트 품질 지표 없음"으로 잡을 수 있으나, 채점 로직의 빈 집합 규칙(`total==0 → 1`) 자체를 겨냥하는 항목은 없음 | O.d.2=0은 있으나 이유가 "지표 미사용"일 뿐. T.10=1("취약점 없음") |
| D6b 전부 SKIPPED인 FAIL_TO_PASS가 RESOLVED_FULL이 될 수 있음 (main 주석이 인정) | T.10 | **예, T.10 문구 그대로** (채점 우회 취약점) | **놓침**: T.10=1 |
| D1·D2 모델이 테스트 파일을 고쳐도 되돌리지 않음(논문 시점), 신규 테스트 파일 선점 경로(v2.0.0) | T.5(에이전트가 정답 정보와 격리) | **예** | **놓침**: T.5=1("에이전트가 호스트 파일시스템과 정답에 접근 불가"). 같은 구조(테스트 파일 접근)의 SWE-Lancer는 T.5=0 |
| D3 "패치 적용"의 정의가 판본마다 다름 | 없음 | 아니오 (채점기 판본·정의 고정 항목 없음) | 해당 없음 |
| D4 P2P가 테스트 패치가 건드린 파일 안으로 한정 | O.d.2, (O.f.1은 E2E용) | 부분 | O.d.2=0 |
| D5 없는 테스트는 실패(보수적) | 없음 | 해당 없음(위험 아님) | — |
| D7 논문 표 22–23의 분류가 코드에 없음 | R.2(오픈소스 평가 하네스) | 부분: 하네스가 보고된 분석을 재현하는가를 묻지 않음 | R.2=1 |
| D8 데이터 개정 이력 없음 | T.6(환경 고정) | 부분 | T.6=1 |
| D9 온도·디코딩 설정이 논문과 코드가 다름 | 없음 | **아니오**: 생성 설정·시드를 고정·보고하라는 항목이 없음 | 해당 없음 |

- **결론:** T.10과 T.5는 문구상 17번이 찾은 핵심 허점(SKIPPED, 테스트 파일 조작)을 겨냥하지만, 논문의 SWE-bench 평가는 둘 다 1점을 주어 **놓쳤습니다.** 이는 점검표 문구의 한계가 아니라 평가 방법의 한계입니다(코드를 읽어 채점하지 않고 문서·논문을 보고 채점했다는 것이 이유 문구에 드러남: "No vulnerabilities are found"). 반대로 점검표에 **없는 것**은 채점기 판본·정의 고정(D3, D8), 생성 설정 보고(D9), 채점기 로직의 경계 조건 검사입니다.
- 5번(`swebench_solved_issues`)이 잰 "해결 패치의 7.8%가 개발자 테스트 전체에서 실패, 29.6%가 정답과 다르게 동작"은 O.d.2=0과 방향이 같고(테스트 품질 미측정), 4번(`impossiblebench`)의 "읽기 전용이어도 부정행위가 남는다(GPT-5 54% → 39%)"는 T.5의 점검 방식이 "접근 가능한가"의 이진이 아니라 "접근한 에이전트가 실제로 쓰는가"까지 봐야 함을 보여 줍니다. 10번(`agentic_eval_randomness`)·21번(`eval_error_bars`)은 R.10(신뢰구간)이 구체적으로 군집 SE·쌍체 비교·반복 실행 분산으로 채워져야 한다는 보완입니다.
