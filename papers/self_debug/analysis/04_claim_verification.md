# 04. 주장 검증 (공식 코드 없음)

## 1. 왜 코드 대조가 아니라 주장 검증인가

공식 코드와 모델 출력 파일이 공개되어 있지 않습니다. `gh api`로 `google-deepmind/self-debug`, `google-research/self-debug`, 저자 계정의 후보 이름을 조회해 모두 404를 받았고, 저장소 검색(제목, "self-debug" + 데이터셋 이름)에서도 이 논문의 구현을 찾지 못했습니다 (2026-11-23). 독립 재구현인 LDB 논문(arXiv:2402.16906, §3.2)도 "공개 코드가 없어 논문의 지침에 따라 재구현했다"고 적습니다. 따라서 코드와 논문의 차이(D1–Dn)는 확인할 수 없고, 논문의 표·그림·본문·부록 프롬프트와 이후 문헌으로 주장을 검증합니다. 문항별 결과가 없으므로 모든 통계는 주변 합에서 낸 가능 범위입니다(`03` §0).

재현에 영향을 주는 정보 부재: API 모델 스냅샷(gpt-3.5-turbo, gpt-4는 날짜 미표기), 시드와 반복 횟수, 분산, 호출·토큰 비용, Spider 채점 지표. code-davinci-002(Codex)는 OpenAI가 종료한 모델로 알려져 있으나 이번에 종료 여부는 확인하지 않았습니다. 부록 E–G에 모든 프롬프트가 있어 프롬프트 재구성은 가능합니다.

## 3. 항목별 상세

### C2와 C7. 신호가 어디서 오는가

Huang et al.의 분류로 보면 세 설정은 신호의 질이 다릅니다.

- **TransCoder UT 계열**: 문제 설명에 10개 단위 테스트가 모두 들어 있고(Sec 4.2) 모두 통과할 때까지 반복하며 평가도 같은 10개입니다. 피드백이 곧 채점입니다. 이 설정의 이득은 "정답 판정으로 멈추는 재시도"입니다. 자기 수정 서베이(Kamoi et al.)를 재검증한 별도 계산에서도 같은 점이 확인되었습니다.
- **MBPP UT 계열**: 테스트 3개 중 1개만 보여 주고 2개는 숨깁니다(Sec 4.3). 채팅 모델(GPT-3.5, GPT-4) 프롬프트에서는 보이는 테스트를 통과하면 한 번 더 "맞나요?"를 묻고, 그래도 통과하지 못하는 새 코드는 쓰지 않습니다(부록 G.5). 숨은 2개 테스트에서 정답이 깨질 수 있어, 이쪽 이득이 더 정직한 값입니다. 총이득은 +5.0 ~ +9.4%p(UT+Expl 설정은 +5.0 ~ +8.4).
- **Spider와 표 3**: 실행 판정 없음. 이득은 작고 구별이 어렵습니다.

이 구분은 "자기 수정이 된다"는 주장의 근거로 Self-Debug를 쓸 때 가장 중요한 단서입니다. 외부 실행기가 있는 과제에서는 재시도가 효과적이고, 그 효과의 대부분은 통과·실패 판정 자체에서 오며, 모델이 스스로 쓴 설명이 더하는 몫은 작습니다.

### C4. 표본 효율

Spider에서 n=1 + 디버깅(80.8)이 n=16 기준선(80.7)과 같고 n=8 + 디버깅(82.5)이 n=32(81.3)를 넘는 것은 그림 6(a)의 라벨로 확인했습니다. 단 (가) 이 기준선들은 실행 다수결로 고른 하나의 후보이고 (나) 디버깅은 한 후보에 설명·피드백·재생성 호출을 더 씁니다. "표본 수"라는 단위로 비교했을 뿐 같은 비용으로 맞춘 것이 아닙니다. 이 논문의 설정에서 Spider 한 턴이면 충분하다는 서술(5.2.1)은 개선이 대부분 한 턴에서 일어난다는 뜻입니다.

### C6. 최고 성능

표 1(a)의 비교는 (1) 학습한 모델, (2) 프롬프트만 쓴 재순위, (3) Self-Debug로 나뉩니다. Self-Debug의 기준선(81.3, 32샘플)이 이미 (2)보다 6.1%p 높습니다. v1 Sec 5.2.1은 "Self-Debug 전의 Codex 결과가 이미 최고 성능에 맞먹는데, 이는 우리의 더 나은 SQL 생성 프롬프트 설계 덕"이라고 직접 적었고 기본키·외래키 관계를 명시하면 성능이 오른다고도 적었습니다. **v2 본문에는 이 문장이 없습니다.** 즉 (2)와의 차이 상당 부분은 프롬프트 설계(Spider의 5-shot 예시와 스키마 표기)이고 디버깅 효과와 섞여 있습니다. 비교 수치는 다른 논문(Ni et al., Shi et al., Zhang et al., Zeng et al.)에서 가져온 것이라 같은 조건에서 다시 측정한 값이 아닙니다.

### C9. 표 3의 숨은 하락

MBPP에서 Codex가 실행 없이 단순 피드백을 받으면 정확도가 61.4에서 57.6으로 떨어집니다. 정답이 오답이 되는 경우가 오답이 정답이 되는 경우보다 최소 19문항 많습니다. 모델이 자기 맞는 코드를 "틀렸다"고 판단해 바꾸는 것으로 보이며, 이는 Huang et al.이 보고한 "정답을 깨뜨림"과 같은 현상입니다. 같은 표에서 Trace는 66.2로 올라, 설명·추적이 판별을 돕는다는 논문의 해석과 방향은 맞습니다(Simple 대 Trace +8.6). 다만 실행 없는 Simple의 하락이 본문에서 설명되지 않습니다.

## 5. 인용 가능 범위 요약

- 인용해도 되는 것: 실행 결과를 피드백에 넣은 반복 수정이 greedy 기준선을 올린다(TransCoder, MBPP). MBPP의 숨은 테스트 설정의 이득이 더 정직한 값. 표 2·3의 값.
- 조건을 붙여야 하는 것: "자기 설명(rubber duck)이 오류를 찾는다"(Spider Codex 한정, 구별 경계), "표본 효율 10배"(Spider 한정), "SOTA"(비교 수치가 다른 논문 것).
- 인용하면 안 되는 것: "실행 없이도 모든 모델이 향상"(Table 3 구별 안 됨, 하락 사례), "설명이 일관되게 이득을 더한다"(설명의 몫 −0.2 ~ +2.0).
