# 01. CPU-ARC 논문 분석

*CPU-ARC: Agentic Reasoning Caching for on-CPU Reasoning Reuse* (Belcak, Heinrich, Muralidharan, Diao, Molchanov; NVIDIA). arXiv:2611.09891 v1 (2026-11-06, 유일한 판), 기술 보고서(arXiv comment "Tech report. 28 pages, 9 figures, 11 tables"). 분석일 2026-11-26. 아래 위치 표기는 논문의 절·표·그림 번호입니다.

## 1. 한 줄 요약

한 번 풀린 문제의 추론 흔적을 빌더 LLM이 **파이썬 코드(의미 함수 네트워크)** 로 바꿔 두면, 같은 풀이가 통하는 새 입력(말만 바꾼 문제, 숫자만 바꾼 문제)은 작은 언어 모델(SLM)과 CPU 실행만으로 풀 수 있고, 그러면 호출 비용이 원본 모델의 1/16–1/291이 된다는 주장입니다(초록, 표 2).

## 2. 문제와 동기 (Sec 1)

- 언어 모델은 같은 종류의 문제도 매번 처음부터 풉니다. 표 1은 MATH-500의 약수 개수 문제에서 "말을 바꾼 것"과 "숫자만 바꾼 것"의 추론이 한 단어도 다르지 않음을 보입니다(예: 196 → 144).
- 기존 시스템 수준 캐시(SLC)를 두 갈래로 나눕니다. **단일체 캐시**(접두사 캐시, 대화 ID 캐시, 의미 유사도 캐시 GPTCache)는 지엽적 변형에 약하거나(유사도를 느슨하게 하면 정확도를 잃음), **모듈형 캐시**(추론을 요약해 다시 LM에 넣음)는 적중해도 LM 생성을 다시 해야 합니다. ARC는 둘의 혼합이라고 소개합니다.
- 두 관찰: O1 풀이를 찾는 일과 풀이를 실행하는 일은 떼어낼 수 있다. O2 한 문제의 추론은 그 문제를 넘어 같은 추론이 통하는 집합 Π에 재사용된다.
- 이 글의 우리 관점: LFI의 "캐싱 프로그램"(클라우드는 풀이를 만들고 로컬은 풀이를 실행한다) 입장을 처음 실험으로 옮긴 논문입니다. 저자도 이번 평가가 "가장 어려운 경우를 일부러 고른 탐색적 작업"이고 장기 목표는 실제 에이전트 비용 절감이라고 적습니다(Sec 1 끝).

## 3. 방법 (Sec 2)

### 3.1 형식 (Sec 2 서두)

- 원본 모델 𝒮(비싸고 똑똑한 모델), 빌더 ℬ(전사를 캐시 항목으로 바꿈), 대상 모델 𝒯(작은 모델, 호출 때 캐시를 돌림), 판정자 𝒥, 정답 오라클 𝒜. 질의 템플릿 q(●1…●n)와 인스턴스 q(o).
- **가정 A1**: 풀 수 있는 모든 q(o)에 대해, SLM 접근이 있는 프로그램 p가 존재해 모든 π ∈ Π에서 p(π) = 𝒜(q(π)). **A2**: p는 ℬ가 q(o)와 𝒮(q(o))에서 만들 수 있다. 논문은 둘 다 "믿음"이라고 부르며 증명하거나 검정하지 않습니다.
- 용어: 같은 추론이 통하는 변형을 equirational이라 부릅니다. 말만 바꾸면 equiparametric(phrasal), 숫자만 바꾸면 equiphrasal(parametric), 둘 다면 equisubstantive(combined).

### 3.2 의미 함수 (Sec 2.1)

- 의미 함수는 `Context → dict[str, Any]`인 파이썬 함수이고, 입력·출력·피호출 함수를 **고정 식별자가 아니라 자연어 설명과 예시**로 참조합니다.
- 런타임 프리미티브: `load`(벡터 유사도로 값 꺼내기), `do`(설명으로 다른 의미 함수를 찾아 호출), `narrate`(설명 기록), `lm`(𝒯에 초등 NLP 질의), `extract`(𝒯로 값 추출), `convert`/`smart_convert`(형 변환, 실패하면 𝒯가 파이썬 리터럴로 고쳐 쓰고 `ast.literal_eval`로 검증), `invoke_tool`.
- 문맥은 층 쌓은 메모리이고 CPU 벡터 저장소(EmbeddingGemma 약 300M, FAISS flat, 768차원, Sec 3.4)가 받칩니다. 이 매칭이 모든 `do`·`load` 호출에서 일어납니다.

### 3.3 구축 (Sec 2.2.1)

다섯 단계입니다. (1) 입력·출력 분리: 전사에서 기대 출력(최종 답)을 떼어 두고, 이 값이 이후 **정답 기준**이 됩니다. (2) 분해: 추론을 함수 크기의 논리 연산 계층으로 나눕니다. (3) 매개변수 인식: 문제 클래스와 변하는 입력 부분, 각 매개변수의 타당 범위를 정합니다. (4) 계획: 만들 함수, 의존 구조, 구현 순서, 세분도(fine/medium/coarse). (5) 구현: ℬ가 에이전트 루프로 함수를 쓰고 정적 검사와 시험을 통과하면 등록합니다.

단계 (5)의 시험이 이 논문을 읽는 데 중요합니다. 후보 함수는 **원래 매개변수로 돌려 전사 조각과 𝒥가 비교**하고, 루트 함수는 **"원본 매개변수 o로 돌려 그 출력을 𝒥가 전사와 정답 라벨(golden label) 둘 다에 대해 판정"** 합니다. 이어 𝒯가 원문에서 매개변수를 뽑는 왕복을 N번 반복해 추출 안정성을 봅니다. 통과하면 템플릿 q(●)과 원문 q(o)가 진입점으로 등록됩니다.

### 3.4 호출과 컴파일 (Sec 2.2.2–2.2.3)

- 호출 4단계: IS1 진입점 검색(질의 임베딩과 등록된 진입점의 코사인 유사도가 **설정 가능한 임계값**을 넘으면 루트 함수 설명을 반환, 아니면 𝒮로 넘김), IS2 매개변수 추출(𝒯), IS3 실행, IS4 출력과 설명 기록.
- 그림 1의 사용 패턴: `cache.use(request)`가 `False`가 아니면 그대로 반환하고, `CacheInvocationError`가 나면 LLM으로 넘깁니다. **넘김 조건은 '적중하지 못함'과 '실행 오류'뿐입니다.** 실행이 끝나 답을 냈지만 틀린 경우를 알아채는 단계는 설명되지 않습니다.
- 컴파일: 유사도 검색을 직접 호출과 딕셔너리 조회로 정적으로 풀어 벡터 저장소 없는 독립 파이썬 모듈로 만듭니다. 대신 이후 갱신은 다시 컴파일해야 합니다.

### 3.5 𝒯의 선택 (Sec 2.2.4, 부록 D)

가장 작은 상용 모델들(Claude Haiku 4.5, Gemini 3.0 Flash Lite, GPT 5.4 Nano)은 "항상 충분"했다고 합니다. 더 줄이려고 **벤치마크 평가 로그의 20%**(target·extractor·converter 역할)를 모아 𝒮로 약 10배의 합성 변형을 만든 뒤 Llama 3.2 1B를 SFT했고(부록 D, 표 11), 이후 실행에서 이 1B를 𝒯로 썼다고 적습니다. 표 2가 어느 𝒯로 만든 값인지는 명시가 없습니다(`03` §7).

## 4. 실험 (Sec 3)

### 4.1 측정 항목 (Sec 3.1)

- **골든 라벨 정렬(C Acc)**: 캐시 출력이 벤치마크 정답과 일치하는 비율. **전사 정렬(Fidelity)**: LM 판정자가 캐시 답이 𝒮의 답과 의미상 같다고 본 비율. S Acc는 𝒮 전사의 정답률.
- **교란 견고성**: 세 모드(phrasal, parametric, combined)의 통과율. 생성은 𝒢 = 𝒮(Claude Opus 4.5), 생성 판정 위원회 2명(Opus 4.5, 만장일치), 시험 판정 위원회 2명(Opus 4.5, 만장일치)(Sec 3.2, 3.4). 교란은 **캐시가 원본에서 이미 정답인 문항에만** 적용합니다(Sec 3.2). parametric 변형의 정답은 𝒢가 쓴 "최종 서술"의 답입니다(Sec 3.2).
- **비용**: 원본 비용, 빌더 비용, 캐시 비용(𝒯 + 추출기 + 변환기). 소매 API 단가로 계산합니다(Sec 3.1, 3.5).

### 4.2 설정 (Sec 3.3–3.5)

- 벤치마크 6종 8개 칸: MATH-500, AIME 2024·2025·2026, GPQA Diamond, GSM8K, MMLU-Pro, SciBench. 문항 수, 하위집합, 반복·시드 수는 AIME·MATH-500·GPQA 외에는 적혀 있지 않습니다.
- 𝒮 = ℬ = Claude Opus 4.5, 확장 사고 예산 4,096 토큰. 𝒯는 처음 Haiku 4.5, 이후 Llama 3.2 1B, 온도 0.0.
- 단가(3.5절): Opus 4.5 입력 $5, 출력 $25, 캐시 쓰기 $6.25, 캐시 읽기 $0.50 (모두 100만 토큰당). 파인튜닝한 Llama 3.2 1B는 입력 $0.023, 출력 $0.194, 프롬프트 캐시 할인 없음. 2026년 3월 API 요금을 씁니다.
- 구축은 **문항마다 독립 캐시**를 만들고 성공하면 마스터 캐시에 합칩니다. 마스터가 호출 때 쓰는 산출물이고 문항별 캐시는 진단용입니다(Sec 3.4).

### 4.4 의도한 위치 (Sec 4)

같은 지시에 다른 내용이 실리는 에이전트·소프트웨어 엔드포인트에 ARC를 얹고, **새 질의나 캐시 실패 때 LLM으로 넘기는 폴백을 둔다**고 상상합니다. 캐시는 항목을 더하며 계속 배울 수 있고(재구축 없음), 사람이나 AI가 코드를 점검할 수 있어 설명 가능하다고 주장합니다. 장기적으로 "의미 모델(semantic model)"과 "neuralware"를 말하지만 이번 실험 범위 밖이라고 선을 긋습니다.

## 6. 한계와 논문이 말하지 않은 것

논문이 스스로 적은 한계는 짧습니다(수학·과학만, 창의 과제 제외, 함수 일반화 문제는 미해결, 컴파일하면 갱신이 불편). 아래는 읽으면서 확인한 빈칸입니다.

1. 캐시를 **평가하는 문항으로 직접 만들었고** 구축 단계 시험이 골든 라벨을 씁니다(3.3절). 그래서 C Acc는 보지 않은 문항의 정확도가 아닙니다(`03` §4).
2. **적용률(coverage), 적중 임계값, 오적중 비율, 구축 실패율**이 없습니다. 표 2 열에 "미적중으로 넘긴 문항"은 없고, 구축 평균을 "새로 만든 캐시 항목 수"로 나눈다는 문장(부록 C 서두)은 구축 실패 문항이 있음을 시사하나 수가 없습니다(`03` §5).
3. 교란 통과율의 **변형 개수·시드·구간**이 없고, 비조건부 정확도는 원본보다 낮을 수 있습니다(`03` §3, §6).
4. 비용은 API 단가표 환산이고 **CPU 실행 시간, 지연, 임베딩·FAISS·Llama 1B의 하드웨어 비용, 판정 위원회 비용**이 없습니다(`03` §1, §2).
5. 재생산 자료가 없습니다. 코드, 캐시 예시, 문항별 결과가 공개되지 않았고 LFI 페이지는 arXiv 링크만 줍니다(`02` §5).
