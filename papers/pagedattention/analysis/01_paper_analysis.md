# 01. 논문 분석 - PagedAttention / vLLM (arXiv:2309.06180)

분석 판: arXiv v1(2023-09-12, 이후 판 없음)과 같은 내용의 SOSP 2023 판(DOI 10.1145/3600006.3613165). 구현 모드(분석일 2026-11-28). 쪽 번호는 `paper/paper.pdf` 기준입니다.

## 1. 문제

LLM 서빙은 한 번에 많은 요청을 묶어야 처리량이 나오는데, 묶을 수 있는 수는 요청마다 커지고 줄어드는 KV 캐시가 GPU 메모리를 얼마나 아끼느냐로 정해집니다(1절, 그림 1). 논문이 지적하는 기존 시스템(FasterTransformer, Orca)의 문제는 두 가지입니다.

1. **단편화**: 딥러닝 프레임워크가 텐서를 연속 메모리에 두기를 요구하므로, 요청마다 최대 길이(예: 2048)만큼 연속 구간을 미리 잡습니다(3절 "Memory Management in Existing Systems"). 낭비는 세 가지로 나뉩니다. 앞으로 채워질 **예약**, 끝내 쓰이지 않는 **내부 단편화**, 할당기(buddy)에서 오는 **외부 단편화**(그림 3). 그림 2: 실제 토큰 상태가 차지하는 비율이 Orca(Max) 20.4%, Orca(Pow2) 26.8%, Orca(Oracle) 38.2%, vLLM 96.3%.
2. **공유 불가**: 병렬 샘플링과 빔 서치는 한 요청 안의 여러 시퀀스가 앞부분 KV를 공유할 수 있지만, 시퀀스마다 별도 연속 구간이라 공유하지 못합니다.

## 2. 방법

**KV 캐시 크기 산술**(3절): OPT-13B의 토큰 하나는 2(K, V) × 5120(hidden) × 40(층) × 2(FP16 바이트) = 800 KB, 2048 토큰이면 요청 하나가 최대 1.6 GB.

**PagedAttention**(4.1절, 식 4): 시퀀스의 KV를 크기 B 토큰의 블록으로 나누고, 블록이 물리 메모리에서 연속일 필요가 없게 합니다. 어텐션을 블록 단위로 계산합니다.

`A_ij = exp(q_i^T K_j / √d) / Σ_{t=1..⌈i/B⌉} exp(q_i^T K_t 1 / √d)`, `o_i = Σ_{j=1..⌈i/B⌉} V_j A_ij^T` (1은 모두 1인 벡터이고 분모는 전체 블록에 걸친 하나의 softmax 정규화입니다).

**KV 캐시 관리자**(4.2, 4.3절, 그림 6, 7): OS의 가상 메모리와 같은 구조입니다. 블록 = 쪽, 토큰 = 바이트, 요청 = 프로세스. 요청마다 **블록 표**(논리 블록 → 물리 블록, 채워진 칸 수)를 둡니다. 새 물리 블록은 이전 블록이 다 찼을 때만 할당(그림 6 단계 ①–④)하므로 요청당 낭비가 마지막 블록 하나 안으로 제한됩니다. 모든 블록이 같은 크기라 외부 단편화가 없습니다. GPU 작업자에는 블록 엔진이, CPU RAM에는 같은 크기의 스왑용 할당기가 있습니다(그림 4).

**디코딩 방식별 적용**(4.4절): `fork`, `append`, `free` 세 연산으로 구현합니다(5.2절).
- 병렬 샘플링(그림 8): 프롬프트 블록을 물리 블록 하나에 두고 **블록마다 참조 횟수**를 둡니다. 공유 블록에 쓰려는 순간 참조 횟수가 1보다 크면 새 블록을 받아 내용을 복사(**블록 단위 copy-on-write**)하고 횟수를 줄입니다.
- 빔 서치(그림 9): 후보들이 프롬프트와 앞쪽 블록을 공유하고, 탈락한 후보의 블록은 참조 횟수가 0이 되면 해제합니다. 기존 시스템은 후보 사이에 KV를 자주 복사해야 했으나 vLLM은 마지막 블록만 복사합니다.
- 공유 접두사(그림 10): 시스템 프롬프트 같은 접두사의 물리 블록을 미리 두고 매핑만 합니다.

**스케줄링과 선점**(4.5절): FCFS, 물리 블록이 바닥나면 가장 늦게 온 요청부터 **전부 또는 전무(all-or-nothing)**로 축출합니다. 같은 요청의 시퀀스 묶음(예: 빔 후보들)은 함께 선점합니다. 복구는 두 가지: **스와핑**(블록을 CPU로 복사, 선점된 시퀀스가 있으면 새 요청을 받지 않음)과 **재계산**(프롬프트 + 생성된 토큰을 한 번의 프롬프트 단계로 다시 계산. OS에는 없는 방법).

**분산 실행**(4.6절): Megatron-LM 식 텐서 병렬. 어텐션 헤드로 나뉘고 단일 KV 캐시 관리자가 논리·물리 블록 매핑을 모든 작업자에게 같은 블록 번호로 공유합니다.

**구현**(5절): Python 8.5K줄 + C++/CUDA 2K줄. 커널 3개: 블록 쓰기와 reshape 융합, 블록 표를 읽는 어텐션(FasterTransformer 커널을 변형, 워프 하나가 블록 하나), 블록 복사 일괄 처리. 각주 1: 층·헤드마다 블록 표를 따로 둡니다.

## 4. 한계 (논문이 인정한 것과 우리가 본 것)

- 논문이 인정: 커널이 20–26% 느림(7.1절). 계산 병목인 워크로드(비 LLM 모델 서빙, 학습)에서는 오히려 느려질 수 있음(8절 토론).
- Orca 기준선은 저자 구현이고 할당기 가정(buddy)이 외부 단편화 수치(그림 2의 36.6%, 41.6%)를 크게 좌우합니다. 우리 재현에서 Oracle의 "외부 + 기타" 36%는 buddy의 2의 거듭제곱 올림에서 나옵니다(`03` §2).
- 그림 12–17의 곡선은 그림만 있고 표나 원자료가 없어 수치를 다시 계산할 수 없습니다. 본문에 적힌 배수만 검산할 수 있습니다.
- 시험한 길이 분포는 ShareGPT와 Alpaca 둘이고 평균만 본문에 나옵니다. 분산과 표본 수, 트레이스 시드, 반복 횟수와 신뢰구간은 없습니다.
- 모든 비교가 NVIDIA A100·GCP 한 환경, OPT와 LLaMA-13B입니다. MHA 모델 전제라 GQA·MLA 모델의 KV 크기에서는 블록 하나가 담는 바이트가 달라집니다.
