# 02. 계보와 관련 분석 - PagedAttention / vLLM (arXiv:2309.06180)

"확인"은 이번 분석에서 논문·공식 코드·API로 직접 본 것이고, "미확인"은 일반 지식이라 인용 전에 원문을 봐야 하는 것입니다.

## 1. 구성 요소별 출처

| 구성 요소 | 논문이 밝힌 출처(위치) | 메모 |
|---|---|---|
| 쪽 단위 가상 메모리, 블록 표 | OS의 페이징 [25](1절, 4.2절) | "블록 = 쪽, 토큰 = 바이트, 요청 = 프로세스". 요청별 블록 표와 참조 횟수, copy-on-write는 `fork` 후 쓰기의 OS 방식 그대로 |
| 반복(iteration) 단위 스케줄링 | Orca [60], cellular batching [16](2.3절) | vLLM과 상호보완이라고 논문이 명시(8절). PagedAttention은 "더 많은 요청이 메모리에 들어가게" 하고 Orca는 "요청을 끼워 넣어" 병렬도를 올림 |
| 어텐션 커널 | FasterTransformer [31]의 커널을 변형(5.1절) | 블록 표를 읽는 부분만 새로 짬. 계산은 같고 논문 7.1절은 커널이 20–26% 느리다고 밝힘 |
| 연속 배치, 가변 길이 | Orca, 패딩 제거 커널(2.3절) | |
| 스와핑·재계산 | 학습 메모리 절약의 swap, recompute [7, 23, 24, 40, 42, 55](9절) | 재계산은 "OS에는 없는 방법"(9절) |
| 블록 단위 타일링 어텐션 | FlashAttention [13](9절) | 논문은 FlashAttention을 "어텐션의 최대 메모리와 I/O를 줄이는" 것으로만 언급하고, 둘이 직교한다고는 쓰지 않음. 이 저장소의 `../flashattention/`(분석)은 계산 순서(타일링, 온라인 softmax)의 I/O 이야기이고 이 논문의 블록은 **KV 저장 배치**의 이야기입니다. 우리 `minimal_impl.py`의 `online` 모드가 둘이 만나는 지점입니다(블록을 타일로 보고 FlashAttention의 온라인 softmax를 돌려도 식 4와 같은 결과, `03` §4) |
| 선점·스와프 스케줄 | FlexGen [46](9절, 스와핑하되 온라인 서빙이 아님), REEF [21], Shepherd [61] | |

## 2. 가까운 대안과 이후 흐름

논문 안 비교는 FasterTransformer와 Orca(저자 재구현)뿐입니다. 아래는 이후 문헌이며 이번 분석에서 직접 확인한 것은 표시했습니다.

| 흐름 | 대표 | 이 논문과의 관계 |
|---|---|---|
| 가상 메모리를 쓰되 어텐션 커널은 안 바꿈 | vAttention(ASPLOS 2025, DOI 10.1145/3669940.3707256, Crossref에서 제목·학회 확인) | "PagedAttention 없이" KV를 연속 가상 주소로 두는 대안. 논문 본문은 미확인 |
| 접두사 재사용을 일반화 | 자동 접두사 캐싱(공식 코드에서 확인: `block_pool.py`의 `cache_full_blocks`, 블록 해시), SGLang의 RadixAttention(미확인) | 논문 4.4절의 "공유 접두사"를 사전 등록에서 해시 기반 자동 매칭으로 확장. 현재 vLLM은 해시를 블록 단위로 둡니다 |
| 블록 크기 선택 | 공식 코드 `CacheConfig.block_size`가 기본값 `None`이고 백엔드가 정함(확인) | 논문의 "16이 기본"은 현재 코드에서 고정 상수가 아님(`04` D6) |
| KV 자체를 줄임 | GQA, MLA, KV 양자화, 윈도·sink 정책. 이 저장소 `../streamingllm/`(롤링 KV 캐시) | 블록 관리와 직교. KV 바이트가 줄면 같은 풀에 들어가는 토큰 수가 늘어 `03` §1의 산술 상수가 바뀜. 예: Llama-2-7B MHA 512 KiB/토큰, Llama-3-8B GQA 128 KiB/토큰(우리 계산) |
| 선점은 재계산 중심으로 | 현재 V1 스케줄러는 선점 시 블록을 해제하고 `num_computed_tokens = 0`으로 되돌림(확인, `04` D3) | 논문의 스와핑 경로는 현재 스케줄러 코드에서 찾지 못함(`04` D3) |
| 요청 단위 이상 가속 | 추측 디코딩(`../speculative_decoding/`, 같은 묶음에서 작성 중), 청크 프리필(미확인) | KV 블록을 더 빨리 채우거나 되돌리는 쪽. 추측 디코딩은 거절된 토큰의 슬롯을 되감아야 해서 블록 관리와 상호작용합니다(미확인, 현재 코드의 `lookahead` 슬롯 흔적만 확인) |

## 3. 이 저장소와 이웃 저장소의 관련 분석

- `../flashattention/` (arXiv:2205.14135, 완료): 정확한 어텐션의 I/O 인식 계산. 이 논문과는 **무엇을 최적화하나**가 다릅니다(FlashAttention = 한 번의 어텐션 호출 안의 HBM 왕복, PagedAttention = 호출 사이에 상주하는 KV 캐시의 배치). 서빙 스택은 둘을 함께 씁니다(현재 vLLM의 어텐션 백엔드는 FlashAttention 계열 커널이 블록 표를 받음, 코드의 `reshape_and_cache_flash` 커널 이름에서 확인, 커널 본문은 미확인).
- `../streamingllm/` (arXiv:2309.17453, 완료): 어떤 K, V를 **남길지**의 정책(싱크 + 윈도). 이 논문은 남긴 K, V를 **어디에 둘지**를 정합니다. 둘을 합치면 "롤링 윈도의 오래된 블록을 해제하고 싱크 블록만 고정"이 되고, 현재 vLLM 코드의 `remove_skipped_blocks`가 슬라이딩 윈도 어텐션에 대해 이를 합니다(코드에서 이름과 위치만 확인, 동작 세부는 미확인).
- `../speculative_decoding/` (같은 묶음에서 작성 중), `../gptq/`, `../awq/`(같은 묶음에서 작성 중): 가중치 양자화는 가중치가 차지하는 비중(그림 1의 65%)을 줄여 KV 풀을 키웁니다. 이 논문의 산술(그림 1, 표 1)이 그 이득을 토큰 슬롯 수로 바꾸는 기준입니다.
